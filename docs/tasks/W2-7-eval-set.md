## A 段要求（零额度）

### 1. 任务集（50 条，`eval/tasks/*.json` 或 `.yaml`）

每条至少含：`id`、`用户输入`、`判定类型`、`硬约束`（可空）、`期望工具`、`不该调的工具`。
覆盖配比建议（自行定稿并写进文档）：单约束 / 多约束 / 含糊需求 / 无解或越界 / 不该调工具（闲聊）/ 注入式输入。

**每条任务必须可由现有三个只读工具（`search_nearby`/`shop_detail`/`voucher_list`）回答** ——
不要设计当前工具集答不了的任务。

### 2. 规则判定器（不许只靠 LLM 评审）

对每条轨迹按可计算的规则判分：
- **任务成功率**：方案满足**全部硬约束**且意图被覆盖
- **约束违反率**：结果里出现超距离 / 超预算 的比例（用工具返回的 `distance`/`avgPrice` 核验，不靠模型自述）
- **工具调用正确率**：该调的调了、不该调的没调、参数对
- **平均步数 / 延迟 / 单次成本**：逐轨迹统计（成本按 token 数与单价算，口径与文档一致）
- **pass^k**：同任务跑 k 次全成功的比例（k 自行定，写进文档）

### 3. 评测台（`src/test/java/com/hmdp/agent/eval/**`）

- 读任务集，逐条驱动**真实的**只读链路（复用 W2-6 的 `E2eHarness` 接线方式：真 `AgentLoop` +
  真 `ToolRegistry`/`ShopTools` + 真 `SpringShopCatalog` + 假业务服务）
- 产出机器可读结果（每条轨迹的步数、事件序列、工具调用与参数、错误、耗时）与汇总表
- 用**脚本化 LLM** 验证：评测台能跑完全部 50 条、能正确判分（**故意放几条必失败的轨迹进去，
  断言判分器真的判它失败** —— 否则判分器形同虚设）
- 汇总表落 `eval/report/`（含"本表由脚本化 LLM 生成，非真实模型分数"的醒目声明）

### 4. 文档

`docs/W2-7-EVAL.md` 写清：50 条任务的配比与理由、每项指标的精确定义与算法、判分器的判定规则、
**以及"为什么本轮只到 A 段"**。
